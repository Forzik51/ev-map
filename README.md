# ev-map

Android-застосунок і Spring Boot API для подій на карті.

## Локальний запуск

Потрібні JDK 21, Android SDK 35, PostgreSQL 17 з PostGIS і `pg_trgm`. Створіть локальні роль та БД `evmap`. Для локального профілю за замовчуванням пароль БД `evmap`. Інші параметри задаються через `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` та `SPRING_DATASOURCE_PASSWORD`. Роль міграцій має мати дозвіл створити схему `evmap` та розширення або адміністратор БД має завчасно встановити `postgis` і `pg_trgm` у `evmap` чи `public`.

Приклад початкового налаштування в `psql` від імені локального адміністратора PostgreSQL:

```sql
CREATE ROLE evmap LOGIN PASSWORD 'evmap';
CREATE DATABASE evmap OWNER evmap;
\connect evmap
CREATE EXTENSION IF NOT EXISTS postgis;
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

```powershell
cd serverApp
$env:SPRING_PROFILES_ACTIVE = 'local'
.\gradlew.bat bootRun
```

Після першого запуску Flyway застосує `B12__schema.sql` і новіші міграції. Для локальної демонстрації можна явно завантажити один приклад події та акаунт `evmap-demo` з паролем `EvmapDemo2026!`.

```powershell
# З каталогу serverApp після запуску міграцій
psql -h localhost -U evmap -d evmap -v ON_ERROR_STOP=1 -f scripts/demo.sql
```

Для відновлення пароля запустіть локальний SMTP-перехоплювач на порту `1025` або задайте `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_SMTP_AUTH`, `MAIL_SMTP_STARTTLS` та `APP_MAIL_FROM`. Параметри й сценарій перевірки описані в [docs/password-reset.md](docs/password-reset.md).

Відкрийте `mobileApp` в Android Studio з Gradle JDK 21 або виконайте в каталозі `mobileApp`:

```powershell
.\gradlew.bat :app:assembleDebug :app:testDebugUnitTest
```

Debug використовує `http://10.0.2.2:8080/` для Android Emulator. Для телефона в тій самій мережі передайте, наприклад, `-PevmapDebugApiUrl=http://192.168.1.10:8080/`, підставивши IP комп’ютера. Альтернатива для підключення по USB — `adb reverse tcp:8080 tcp:8080` і `-PevmapDebugApiUrl=http://127.0.0.1:8080/`. Адресу також можна вказати в `EVMAP_DEBUG_API_URL`.

## Production

Запускайте сервер із `SPRING_PROFILES_ACTIVE=prod`. Задайте `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`, `MAIL_HOST` і `APP_MAIL_FROM`. Змінні `MAIL_PORT`, `MAIL_SMTP_AUTH` та `MAIL_SMTP_STARTTLS` за замовчуванням визначають SMTP на порту 587 з авторизацією і STARTTLS. Налаштуйте облікові дані SMTP у `MAIL_USERNAME` і `MAIL_PASSWORD`. Для `APP_JWT_SECRET` та `APP_PASSWORD_RESET_SECRET` використайте окремі стабільні випадкові ключі зі сховища секретів. Ключ відновлення має бути 32 байти в Base64. Каталог `APP_MEDIA_ROOT` має бути доступний для запису і зберігатися між розгортаннями.

Для Android release задайте HTTPS-адресу через `-PevmapReleaseApiUrl` або `EVMAP_RELEASE_API_URL`. Приклад команди для Android, де `api.example.com` потрібно замінити на ваш домен:

```powershell
.\gradlew.bat :app:bundleRelease -PevmapReleaseApiUrl=https://api.example.com/
```

### Оновлення бази

Flyway для нових БД починає з `B12`, для БД із застосованою V2 продовжує з наявної історії. Автоматичний baseline вимкнено. Якщо в старій БД очікує виконання V2, сервер зупиниться, оскільки цей демоскрипт містить `TRUNCATE`.

Для перевіреної **копії БД зі схемою V1** зупиніть застосунок, зробіть резервну копію й підтвердьте, що є вихідні таблиці V1 та немає частково застосованих V2 або V3. Якщо в копії є таблиця історії Flyway, перенесіть її разом з індексами в окрему схему:

```sql
CREATE SCHEMA evmap_migration_archive;
ALTER TABLE evmap.flyway_schema_history SET SCHEMA evmap_migration_archive;
```

Скеруйте Flyway CLI на цю копію через `FLYWAY_URL`, `FLYWAY_USER`, `FLYWAY_PASSWORD` і `FLYWAY_SCHEMAS=evmap`, потім виконайте `flyway -baselineVersion=2 baseline`. Запустіть сервер на копії, щоб він застосував V3 і новіші міграції. Перевірте кількість записів і основні сценарії перед перенесенням оновлення на робочу БД.

## Створення подій, версія 1.1

Форма підтримує фото без порожніх заповнювачів, необов’язкові дату й час, часовий пояс, вибір точки або власної області на карті, адресний пошук, категорії й теги. Назва обов’язкова до 100 символів, опис — до 2000; дозволено 1–3 категорії, до 5 тегів по 30 символів і до 10 фотографій по 5 МБ. Перше фото в заданому порядку є обкладинкою. Для минулої дати форма просить підтвердження.

Режими розкладу API: `UNSPECIFIED` — без дати; `DATE` — `startsOn`, необов’язковий `endsOn` і `timeZone`; `DATETIME` — `startsAt`, необов’язковий `endsAt` і `timeZone`. Для календарних дат сервер обчислює часові межі в заданому поясі, а клієнт відображає саме календарні дні. Для фільтра активності подія без завершення вважається одноденною. Події без дати залишаються у загальних списках, але не потрапляють у вибірки за датами. Стрічка використовує справжній `createdAt`.

`clientRequestId` зберігається разом із чернеткою до першого запиту. Повторна публікація з тим самим ключем і вмістом повертає той самий ID. Інший вміст із тим самим ключем повертає 409, а повтор після видалення події — 410. Частково завантажені фото узгоджуються з сервером за `uploadId`, тому повтор не створює зайві події або фотографії.

Чернетки й копії вибраних фото зберігаються у внутрішньому сховищі Android окремо для кожного акаунта. Форма відновлюється після повторного відкриття; закриття форми зберігає введене. Для очищення є явна дія «Видалити чернетку». Після повного успіху локальні файли завантажених фото й чернетка очищуються. Хмарної синхронізації чернеток немає.

Пошук місць виконується кнопкою через `/api/locations/search`. Підтвердження результату — `/api/locations/resolve`, власна геометрія — `POST /api/locations`. Підтримані Point, LineString, MultiLineString, Polygon і MultiPolygon. Місця мають окремий тип, назву й адресу; геометрія перевіряється на координати, самоперетини та кількість точок. Карта показує межі й лінії, а просторовий пошук враховує всю геометрію.

Адаптер геокодування налаштовується через `APP_GEOCODING_URL` і `APP_GEOCODING_USER_AGENT`; за замовчуванням використовується публічний Nominatim. Його [умови використання](https://operations.osmfoundation.org/policies/nominatim/) вимагають усвідомленого вибору сервісу власником застосунку, ідентифікації клієнта, атрибуції, обмеження сумарного трафіку й забороняють автодоповнення через публічний API. Реалізація використовує ручний пошук, спільний ліміт до одного нового запиту за 1,1 секунди та кеш відповідей на 7 діб до 500 записів. Провайдер змінюється на сервері без нового APK. Якщо пошук недоступний, можна вибрати точку або намалювати область вручну.

Категорії спільні для подій і фільтрів; теги створюються при збереженні події та повторно використовуються після нормалізації. Фільтрація за кількома тегами знаходить збіг хоча б одного з них; категорії й теги разом застосовуються через AND. Пропозиції категорій надсилаються через `/api/event-taxonomy/category-requests`; користувач із роллю ADMIN підтверджує або відхиляє їх у розділі модерації.

Міграції V14–V19 зберігають наявні записи й додають нові поля. Телефон і дата народження необов’язкові; заповнені значення перевіряються на Android і сервері, майбутня дата народження відхиляється. Клієнтські моделі приймають nullable-поля. Новий APK має versionCode 2 і передає `X-Evmap-Client-Version: 2`. Після оновлення клієнтів установіть `APP_MIN_CLIENT_VERSION=2`: сервер відповідатиме старим API-клієнтам кодом 426 `UPDATE_REQUIRED`. Без цього параметра мінімальна версія не обмежується. Для ручних API-запитів також потрібен цей заголовок; `/health` доступний без нього.

Перед випуском: резервна копія, перевірка міграцій на копії БД, збірка й установлення нового APK, оновлення сервера та перевірка основних сценаріїв. Попередній JAR для повернення має підтримувати нову схему й nullable-дані: просте повернення старої версії 1.0 після створення подій без дати не є сумісним відкатом.

Сценарій `deploy/lightsail/verify-event-form-migrations.sh` перевіряє V14–V19 на тимчасовій копії робочої БД: після завантаження сценарію й цих шести SQL-файлів на Lightsail запустіть `bash verify-event-form-migrations.sh /directory/with/migrations`. Він звіряє кількість користувачів, подій, фотографій і місць, потім видаляє тимчасову БД та дамп. Робочу БД не змінює.

## Автоматичні перевірки

На Windows `serverApp/scripts/test-password-reset.ps1` запускає всі серверні тести на тимчасовій PostgreSQL/PostGIS. CI виконує перевірки Android і сервера, включно з чистою БД та оновленням старих баз. SMTP у тестах підмінено. Інтеграційні тести сервера потребують `EVMAP_TEST_DB_URL`, яку задає тестовий сценарій або CI.

## AWS Lightsail

Розгортання у `eu-north-1`: `https://13.50.153.52/`, перевірка готовності — `GET /health`. Корінь `/` не є вебсторінкою; API використовує `/api/**`, WebSocket — `/ws`. Нова база містить довідники категорій і не містить демонстраційних акаунтів або подій.

Сервер `evmap-backend` використовує Ubuntu 24.04, Java 21, PostgreSQL 17/PostGIS, Nginx і systemd. Тариф `micro_3_0`: 1 ГБ RAM, 40 ГБ SSD, $7/місяць. Тариф 2 ГБ був недоступний для цього проєкту AWS. Пам’ять JVM обмежена, налаштовано 2 ГБ swap. Приватний bucket `evmap-backups-447935657035` коштує $1/місяць і включає 5 ГБ зберігання. Базова сума — $8/місяць до податків; перевищення квот зберігання, трафіку та листів оплачується окремо. AWS Budget `evmap-monthly` має ліміт $20 і фактичні сповіщення $15/$18 на `evntmap@gmail.com`, без віднімання кредитів. Ці сповіщення не зупиняють ресурси автоматично.

Статична IPv4 `evmap-ip` прикріплена до сервера. HTTP використовується для ACME-перевірки та перенаправлення на HTTPS. Довірений IP-сертифікат Let's Encrypt автоматично поновлюється таймером `evmap-cert-renew.timer` двічі на добу; його строк дії — приблизно 6 днів. База й Java API слухають лише `127.0.0.1`; ззовні відкриті 80/443 та SSH з IP `83.175.176.8/32`. Якщо ваша зовнішня IP зміниться, оновіть SSH-правило у Lightsail.

### Керування й оновлення

SSH-ключ зберігається поза репозиторієм: `%USERPROFILE%\.ssh\evmap-lightsail-eu-north-1.pem`. У PowerShell:

```powershell
$evmapKey = "$env:USERPROFILE/.ssh/evmap-lightsail-eu-north-1.pem"
ssh -i $evmapKey ubuntu@13.50.153.52
```

На сервері:

```bash
sudo systemctl status evmap
sudo journalctl -u evmap -n 100 --no-pager
sudo systemctl restart evmap
sudo systemctl list-timers 'evmap-*'
sudo /opt/certbot/bin/certbot renew --dry-run --no-random-sleep-on-renew
```

Для оновлення з кореня репозиторію, маючи JDK 21 у `JAVA_HOME`:

```powershell
.\deploy\lightsail\deploy.ps1 -IpAddress 13.50.153.52
```

Сценарій збирає JAR, чекає успішної резервної копії, завантажує JAR і перевіряє локальний та зовнішній `/health`. У разі невдалого запуску повертається попередній JAR. Міграції БД автоматично не відкочуються; перед змінами схеми потрібно перевіряти сумісність із попередньою версією. Секрети `/etc/evmap/app.env` мають права `0600`, фотографії зберігаються у `/var/lib/evmap/media`. Повторне розгортання їх зберігає. JVM не має прав змінювати JAR або файл секретів.

### Резервні копії й відновлення

`evmap-backup.timer` щодня о 03:00 UTC створює узгоджену копію PostgreSQL та медіа. Для цього застосунок короткочасно зупиняється і знову запускається. Копія надсилається у приватний bucket із шифруванням SSE-S3. Сервер отримує доступ через прикріплення Lightsail instance до bucket, без AWS access keys. Файли секретів не включаються. Локальні копії зберігаються до 3 діб, об’єкти `daily/*.tar.gz` у сховищі видаляються після 14 діб під час наступного успішного копіювання. Версіонування bucket вимкнене. Після збоїв копіювання потрібно перевірити його журнал і доступність сховища.

```bash
sudo systemctl start evmap-backup.service
sudo journalctl -u evmap-backup.service -n 30 --no-pager
sudo aws s3 ls s3://evmap-backups-447935657035/daily/ --region eu-north-1
```

Для відновлення завантажте вибрану копію на сервер у каталог із правами `0700`, розпакуйте та спочатку відновіть `database.dump` в **окрему порожню БД**. Створіть її з власником `evmap`, від адміністратора встановіть `postgis` і `pg_trgm` у `public`, а `pg_restore` запускайте від адміністратора з `--no-owner --no-privileges --role=evmap`, щоб таблиці належали користувачу застосунку. Перевірте записи та медіа. Потім зупиніть застосунок, збережіть поточну БД і медіа, перемкніть `SPRING_DATASOURCE_URL` на перевірену БД, відновіть `var/lib/evmap/media`, установіть власника `evmap:evmap` і запустіть застосунок. Поточна БД залишається доступною для повернення до попереднього стану. На новому сервері згенеруйте секрети через `bootstrap.sh` і налаштуйте SMTP; використання нових JWT/reset-ключів припиняє чинність попередніх сесій і запитів відновлення пароля.

### SMTP і перевірка запуску

Відправник `evntmap@gmail.com` підтверджений у SES `eu-north-1`. Окремий IAM-користувач `evmap-smtp` має лише `ses:SendRawEmail` для цієї адреси; політика прикріплена безпосередньо до користувача, оскільки новий AWS experience обмежує IAM-групи. SES працює у sandbox: листи можна надсилати лише підтвердженим адресам. Для довільних користувачів потрібен вихід SES із sandbox. SMTP-пароль зберігається у файлі середовища сервера, локальна приватна копія — `%USERPROFILE%\.ssh\evmap-smtp.env`.

Конфігурації у `deploy/lightsail` призначені для нової Ubuntu 24.04; початковий запуск — `sudo bash bootstrap.sh SENDER_EMAIL`, далі `configure-tls.sh STATIC_IPV4 EMAIL`, `install-backups.sh BUCKET` та `release.sh BOOT_JAR`. Перед цим потрібно створити Lightsail instance, прикріпити статичну IP, налаштувати firewall і приватний bucket, надати instance доступ до нього, перевірити SES і задати SMTP. `bootstrap.sh` зберігає наявні секрети, але повторне налаштування PostgreSQL перезапускає базу, тому його не слід використовувати як звичайне оновлення JAR.

`smoke-test.py` і `restore-test.py` перевіряють реальний сервер на тимчасових даних. Вони потребують root і явної email-адреси для тестових листів. Перевірено реєстрацію, вхід, події, PostGIS-пошук, фото з Bearer-авторизацією, чат через HTTPS/WSS і заборону чужого доступу, зміну пароля через SMTP, відкликання токенів, збереження даних після перезапуску й відновлення завантаженої хмарної копії в ізольовану БД.
