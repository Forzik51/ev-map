# Відновлення пароля

Сценарій Android: email → восьмизначний код із листа → новий пароль → вхід.
Код і пароль не передаються в URL. Проміжний дозвіл зберігається лише в пам'яті ViewModel;
після завершення процесу застосунку відновлення потрібно розпочати знову.

## Сервер і пошта

Flyway застосовує `V9__password_reset.sql`: додає запити відновлення, зашифровану чергу
листів, `app_user.auth_version` та унікальний індекс email без урахування регістру.
Перед оновленням наявної бази перевірити дублікати:

```sql
SELECT lower(email), count(*) FROM evmap.app_user
GROUP BY lower(email) HAVING count(*) > 1;
```

Якщо дублікати є, їх потрібно розв'язати перед міграцією. Міграція не об'єднує облікові записи.

Для стабільної роботи задайте окремий випадковий секрет. PowerShell:

```powershell
$resetKeyBytes = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($resetKeyBytes)
$env:APP_PASSWORD_RESET_SECRET = [Convert]::ToBase64String($resetKeyBytes)
```

Зберігайте це значення в налаштуваннях середовища/сховищі секретів, а не в Git.
Всі екземпляри сервера мають використовувати той самий ключ. Без нього сервер генерує
тимчасовий ключ для локальної розробки: після перезапуску старі коди не працюватимуть,
а недоставлені листи зі старим ключем будуть скасовані. Зміна ключа також анулює старі коди.

Налаштування SMTP: `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`,
`MAIL_SMTP_AUTH`, `MAIL_SMTP_STARTTLS`, `APP_MAIL_FROM`. У профілі `local` за замовчуванням використовується
локальний SMTP на `localhost:1025`. Для локального ручного тесту потрібен SMTP-перехоплювач;
для реальної доставки — налаштований поштовий сервер. У production API має працювати через HTTPS.

Листи зберігаються в outbox у тій самій транзакції, що й запит/зміна пароля.
Тіло зашифроване AES-GCM, код перевіряється через HMAC-SHA256 з прив'язкою до requestId,
а випадковий resetToken зберігається як SHA-256. Воркер перевіряє чергу кожні 5 секунд,
робить до 3 спроб доставки з паузами 30/60 секунд, скасовує неактуальні коди й очищає
записи старші 7 днів. HTTP 202 означає прийняття запиту, а не підтвердження доставки листа.
Паролі, коди й токени не записуються в журнали.

## API

| POST | JSON | Успішна відповідь |
| --- | --- | --- |
| `/api/auth/password/forgot` | `{"email":"person@example.com"}` | 202: `requestId`, `resendAfterSeconds`, однакове повідомлення для наявної й невідомої адреси |
| `/api/auth/password/verify` | `{"requestId":"UUID","code":"12345678"}` | 200: `resetToken`, `expiresInSeconds` |
| `/api/auth/password/reset` | `{"resetToken":"...","newPassword":"..."}` | 204 |

Неправильний/прострочений/використаний код: 400 з `code=INVALID_OR_EXPIRED_CODE`.
Недійсний дозвіл: 400 з `code=INVALID_OR_EXPIRED_RESET_TOKEN`.
Ліміт запитів: 429 з `Retry-After` і `retryAfterSeconds`.

Параметри `app.security.password-reset` у `application.yml`:
код діє 10 хвилин, дозвіл — 5 хвилин, 5 перевірок коду, повторне надсилання через 60 секунд,
до 5 запитів на email і 20 на IP за годину. Ліміти застосовуються й до невідомих адрес
та синхронізуються через блокування PostgreSQL. Використовується `remoteAddr`, а не довільний
`X-Forwarded-For`; за reverse proxy налаштуйте довірене визначення IP на рівні інфраструктури.

Новий запит анулює попередній; код обмінюється на дозвіл лише один раз. Успішне скидання
анулює всі запити відновлення й refresh-токени користувача, збільшує auth_version та закриває
його WebSocket-з'єднання після commit. REST і STOMP перевіряють версію JWT в БД, тому старий
access token також перестає працювати одразу. Для запобігання перегонів login/refresh/reset
використовують спільне блокування рядка користувача. Після скидання автоматичного входу немає.

Реєстрація і скидання використовують однакову перевірку пароля: мінімум 6 символів,
непорожній пароль і максимум 72 UTF-8 байти, відповідно до наявного BCrypt.

## Перевірки

```powershell
# Сервер: тимчасовий PostgreSQL/PostGIS, перевірки чистої й оновленої БД, HTTP і WebSocket.
# Робоча база evmap не використовується. PostgreSQL зупиняється у finally.
cd serverApp
./scripts/test-password-reset.ps1 -PostgresBin 'C:/Program Files/PostgreSQL/17/bin'
```

Потрібні JDK 21 і PostgreSQL із PostGIS та pg_trgm. Дані/логи тестового кластера залишаються
в ігнорованому `serverApp/build`; звіт Gradle — `build/reports/tests/test/index.html`.
Інтеграційний клас запускається тільки з `EVMAP_TEST_DB_URL`, перевіряє локальну адресу
і назву `evmap_password_reset_test`. SMTP у цих тестах підмінено; перевіряються також збої й повторні спроби.
Звичайний `./gradlew.bat test` без цієї змінної пропускає тести, яким потрібна БД,
і не підключається до робочої бази. Контекстний тест використовує ту саму перевірку адреси.

Android: `:app:testDebugUnitTest :app:assembleDebug` через Gradle 8.13.
Тести ViewModel перевіряють переходи, очікування відповіді сервера, підтвердження пароля,
ліміти, повторне надсилання та скасування запиту при виході зі сценарію.
